# Spec: Trade Data Model

## Requirements

The trade model is the canonical data shape used across the entire system. It must be defined once in the `shared/` package and imported by both the frontend and backend. It is the source of truth for:

- MongoDB document structure
- API request and response shapes
- Frontend form validation
- TypeScript types throughout the codebase

See: [ADR 002](../decisions/002-database-mongodb-zod-shared-schemas.md)

## Model Definition

The assessment defines a minimum interface. This project extends it with the additional fields present in the sample data.

> **Field naming note:** The assessment's minimum interface names the timestamp field `tradeDate`. The sample data uses `tradeTimestamp`, which is more precise (it carries a full datetime, not a date). This project adopts `tradeTimestamp` to match the sample data and to accurately reflect the field's content. This is a deliberate, documented extension of the minimum interface.

```typescript
// shared/src/schemas/trade.ts

import { z } from "zod";

export const TradeSchema = z.object({
  id: z.string(),
  symbol: z.string().min(1).max(10),
  side: z.enum(["BUY", "SELL"]),
  quantity: z.number().int().positive(),
  price: z.number().positive(),
  trader: z.string().min(1),
  book: z.string().min(1),
  counterparty: z.string().min(1),
  tradeTimestamp: z.string().datetime(),
  status: z.enum(["ACTIVE", "CANCELLED"]),
});

export type Trade = z.infer<typeof TradeSchema>;
```

### Field Reference

| Field | Type | Constraints | Notes |
|---|---|---|---|
| `id` | `string` | Required | Generated by the backend (`TRD-XXXXXX` format) |
| `symbol` | `string` | 1–10 chars | Equity ticker, e.g. `AAPL` |
| `side` | `"BUY" \| "SELL"` | Required | Direction of the trade |
| `quantity` | `number` | Integer, > 0 | Number of shares |
| `price` | `number` | > 0 | Price per share at execution |
| `trader` | `string` | Required | Trader identifier, e.g. `JSMITH` |
| `book` | `string` | Required | Trading book, e.g. `EQUITIES_UK` |
| `counterparty` | `string` | Required | Counterparty firm name |
| `tradeTimestamp` | `string` | ISO 8601 datetime | Time of trade execution |
| `status` | `"ACTIVE" \| "CANCELLED"` | Required | Lifecycle state |

## Derived Schemas

The full `TradeSchema` is used for reads. Writes use narrower schemas derived from it to prevent clients from supplying server-managed fields.

```typescript
// Schema for creating a new trade — id and status are set by the backend
export const CreateTradeSchema = TradeSchema.omit({ id: true, status: true });
export type CreateTradeInput = z.infer<typeof CreateTradeSchema>;

// Schema for amending a trade — only mutable fields
export const AmendTradeSchema = TradeSchema.pick({
  quantity: true,
  price: true,
  trader: true,
  book: true,
  counterparty: true,
}).partial();
export type AmendTradeInput = z.infer<typeof AmendTradeSchema>;
```

## Seed Data

On application startup, if no trades exist in the database, the backend generates a realistic dataset of 100–500 trades using the schema above. Generated values should be randomized across:

- A pool of realistic equity symbols (e.g. AAPL, MSFT, TSLA, GOOGL, AMZN)
- A pool of trader identifiers
- A pool of trading books and counterparties
- Timestamps distributed across the current trading day
- A mix of BUY/SELL sides and ACTIVE/CANCELLED statuses

## Dependencies and Blockers

- **Blocks:** all other feature specs — no request can be made until this model is defined and exported from `shared/`
- **Requires:** `shared/` package configured as a workspace dependency in both `frontend/` and `backend/`
- **Requires:** ADR 002 (Zod over Mongoose) to be accepted

## Acceptance Criteria

- [ ] `TradeSchema`, `CreateTradeSchema`, and `AmendTradeSchema` are exported from `shared/`
- [ ] All TypeScript types are inferred from Zod schemas — no manually written interfaces that duplicate schema fields
- [ ] `symbol`, `side`, `quantity`, `price`, `trader`, `book`, `counterparty`, `tradeTimestamp`, and `status` are all validated at runtime
- [ ] `quantity` and `price` reject zero and negative values
- [ ] `tradeTimestamp` rejects non-ISO-8601 strings
- [ ] Both `frontend/` and `backend/` resolve the `shared/` package without path hacks

## Testing

- Unit tests for `TradeSchema` covering valid inputs, each invalid field in isolation, and boundary values (`quantity: 0`, `price: -1`, empty strings, invalid datetime format)
- Unit tests for `CreateTradeSchema` confirming `id` and `status` are rejected if supplied
- Unit tests for `AmendTradeSchema` confirming only permitted fields are accepted and all are optional
